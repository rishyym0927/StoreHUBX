## Phase 3 — System design / scaling

- [x] **6. Add retry + exponential backoff for failed build jobs** — builds directly on the per-job timeout added recently; currently a failed job just dies with no retry.
  - Added `Attempts`/`MaxAttempts`/`NextAttemptAt` to `BuildJob`; `worker.fail()` now requeues with `10s * 2^attempt` backoff (capped at 2m) up to `MaxAttempts` (default 3) before setting `BuildError`.
- [x] **7. Add a caching layer (Redis) in front of `GET /components` and `GET /components/:slug`** — read-heavy, write-rare endpoints.
  - New `internal/cache` package (self-hosted Redis via docker-compose). List cache invalidates via an epoch counter bumped on any component write; per-slug cache invalidates on likes/repo-link changes and on new unique visitors. Degrades gracefully to no-cache if Redis is unreachable.
- [x] **8. Move the build queue off Mongo polling** onto a real queue (Redis/RabbitMQ/SQS) — reduces DB load, adds proper at-least-once delivery semantics.
  - `EnqueueBuild`/`AddVersion`/`AutoDeploy` now `XADD` to a `builds:stream` Redis Stream; the worker blocks on `XREADGROUP` for near-instant pickup, with a slower (30s) Mongo poll kept as a fallback sweep for retries and dropped messages. Falls back entirely to the original fast poll when Redis isn't configured.
- [x] **9. Put a CDN in front of MinIO/S3** for built component bundles — improves preview load time.
  - `s3.go`'s `publicURL()` now honors `CDN_BASE_URL` when set. Code-side only — actually fronting MinIO with a CDN (e.g. Cloudflare) requires a domain/account on the user's side.
- [x] **10. Add build pipeline observability/metrics** (success/failure rate, queue depth, build duration) — currently just a console heartbeat print.
  - New `internal/metrics` package (Prometheus client) exposing `GET /metrics`; instrumented in the worker's success/fail paths and heartbeat. Added self-hosted `prometheus`+`grafana` services to `docker-compose.yml`.

## Phase 4 — New features

- [x] **11. Component ratings/reviews** (beyond likes).
  - Added `Rating` model (unique per componentId+userId) with `internal/handlers/rating_handler.go` (upsert/list/delete), denormalized `averageRating`/`ratingCount` on `Component` recalculated on every write. Frontend: `ratingApi`, `RatingStars`, `ComponentRatings` (review list + rate form) wired into the component detail page and card.
- [x] **12. Webhook-based auto-deploy** on GitHub push — upgrade from the current manual "Auto-Deploy" trigger.
  - Per-repo-link `WebhookSecret` (generated on link), public `POST /webhooks/github/:slug` verifying `X-Hub-Signature-256` via constant-time HMAC compare, reusing a shared `createVersionAndBuild` helper (extracted from `AutoDeploy`). Owner-only `GET /api/components/:slug/webhook` + a `WebhookSetup` frontend panel surface the URL/secret to copy into GitHub's webhook settings.
- [x] **13. Build caching by commit SHA** — skip rebuilding when the same commit is redeployed.
  - `internal/handlers/build_cache.go`'s `findCachedBuild` checks for another version of the same component already built successfully from the identical `commitSha`; wired into `createVersionAndBuild` (auto-deploy/webhook), `AddVersion`, and `EnqueueBuild` so a matching commit copies `previewUrl`/`buildState` instead of enqueuing a new `BuildJob`.
- [x] **14. Private/team components** — visibility control beyond fully public.
  - `Component.Visibility`/`Collaborators` fields; new `internal/middleware/optional_auth.go` (never rejects, just attaches identity if present) applied to `GET /components/:slug` and `GET /users/:id` so owners/collaborators see their private components while everyone else 404s; `GET /components` always excludes private docs. Owner-only `PATCH .../visibility` + collaborator add/remove routes. Frontend: visibility toggle + collaborator management in `OwnerActions`, PRIVATE badge on card/detail page.
- [x] **15. Usage analytics dashboard** for component owners — view/like data is already tracked, just not visualized.
  - Protected `GET /api/me/analytics` aggregates per-owned-component view/like/rating/comment totals (`internal/handlers/analytics_handler.go`). New `/me/analytics` page with stat tiles, linked from `/me`. MVP totals only — no new time-series tracking added since none of the underlying data has historical buckets.
- [x] **16. Set up Grafana dashboards for the Prometheus metrics from item 10** — Prometheus+Grafana are already running (`docker compose up`) and `/metrics` is exposing data, but no dashboard exists yet to actually look at it. Steps: open `http://localhost:3001` (admin/admin), add a Prometheus data source pointing at `http://prometheus:9090` (the in-network service name, not localhost), then create panels for `storehubx_builds_total` (rate, split by `status`), `storehubx_build_queue_depth` (gauge over time), and `storehubx_build_duration_seconds` (histogram/heatmap). Save it as a dashboard JSON under `StoreHUBXBackend/grafana/` so it's provisioned automatically instead of manually re-built every time `docker compose down -v` wipes the `grafana_data` volume.
  - Added `grafana/provisioning/{datasources,dashboards}` (auto-registers the Prometheus datasource + `build-pipeline.json` with the three requested panels) and mounted it into the `grafana` service in `docker-compose.yml`. Verified end-to-end with `docker compose down -v && up -d prometheus grafana`: both the datasource and dashboard reappear with zero manual setup.

## Phase 5 — Motion & interaction polish

Same black/white brutalist system (2px borders, hard offset drop-shadows, mono uppercase type, sharp corners, dark mode via `next-themes`) — no new colors, no rounded corners, no soft shadows. This phase is about making the *existing* language feel more deliberate: consistent hover/press physics, entrance motion, and a couple of signature brutalist flourishes the current UI doesn't use yet.

- [ ] **25. Unify the hover/press "physics" across all interactive elements** — right now buttons/links randomly use one of three different hover treatments (`hover:scale-105`, `hover:-translate-y-1 + shadow-lift`, or plain `transition-colors`) with no clear rule for which gets which (compare `navbar.tsx`'s `Browse`/`+ New` links using scale vs. `like-button.tsx`/`pagination.tsx` using shadow-lift vs. `tabs.tsx` using only color). Define one rule (e.g. primary/filled actions get shadow-lift, secondary/outline actions get scale, text-only links get underline/opacity) as a small set of shared utility classes or a `Button`-style wrapper, then sweep all `.tsx` files onto it.
- [ ] **26. Add staggered entrance animation for grid/list content** — Browse grid, home page featured components, and search results currently just pop in with no transition once loading flips to false, while the skeleton (item 23) disappears abruptly. Add a subtle fade+slide-up with per-card stagger delay (CSS `animation-delay` keyed by index, consistent with the existing hand-rolled `@keyframes marquee` pattern in `globals.css` rather than pulling in a library) so content feels like it's assembling, not flashing in.
- [ ] **27. Animate the sharp-corner shadow offset as a continuous transform, not a snap** — the signature `shadow-[8px_8px_0px_0px_...]` hover effect (cards, hero CTAs, buttons) currently has the shadow appear at full offset instantly via `transition-all`, which doesn't tween box-shadow smoothly in most browsers and reads as a jump-cut. Replace with a transform-based approach (an absolutely-positioned pseudo-shadow layer or a translated duplicate border) that genuinely animates from 0 to 8px offset, and standardize the duration/easing (e.g. `duration-150 ease-out`) across `component-card.tsx`, `page.tsx` hero buttons, and `pagination.tsx`.
- [ ] **28. Add a page-level route transition** — navigating between `/`, `/components`, and `/components/[slug]` currently hard-cuts with no shared transition, which feels abrupt for a design system this deliberate about motion elsewhere (marquee, hover lifts). Add a lightweight fade/slide wrapper around `{children}` in `app/layout.tsx` (e.g. via CSS view-transitions or a minimal `framer-motion`/`AnimatePresence` if a motion library is pulled in — evaluate bundle cost first) so route changes feel continuous rather than a flash of unstyled content.
- [ ] **29. Give the loading skeletons (item 23) a shimmer instead of a flat pulse** — `component-card-skeleton.tsx` and the home page's loading blocks currently use Tailwind's default `animate-pulse` (flat opacity fade); replace with a diagonal shimmer sweep (a moving `linear-gradient` band, black/white only) that reads as "actively loading" rather than "half-rendered," consistent with the brutalist high-contrast aesthetic.
- [ ] **30. Add a signature micro-interaction to the like/rate actions** — `like-button.tsx` and `rating-stars.tsx` currently just flip state instantly (`scale-110` on the icon); add a short, snappy confirmation animation (e.g. a brief hard-shadow "punch" on the whole button, or a quick fill-sweep on the star row) so these key engagement actions have tactile feedback matching the site's bold personality, not a generic library ripple/glow.
- [ ] **31. Smooth the theme toggle transition** — `theme-toggle.tsx` currently swaps `.dark` class instantly, causing every border/bg/text color on screen to snap between black/white with no transition, which looks jarring given how much of the page (borders, shadows, backgrounds) inverts at once. Add a global `transition-colors duration-200` on `html`/`body` (careful to exclude it from elements that already animate box-shadow via item 27, to avoid double-transitioning) so the light/dark swap reads as a deliberate flip rather than a flicker.

## Phase 6 — UX consistency & feedback

Same palette and layout language as above; this phase closes gaps in how the UI *communicates state* to the user — feedback for actions, consistent empty/error handling, and small friction points found by reading the actual page/component files.

- [ ] **32. Replace `alert()`/`console.error`-only error handling with in-UI toast/inline feedback** — several action handlers (e.g. like/rate/comment failures, GitHub link errors) currently fall back to a native `alert()` or a silent `console.error`, which is jarring (browser-chrome popup breaks the custom UI) or invisible. Add a minimal brutalist toast primitive (bordered box, hard shadow, auto-dismiss, matching `component-card.tsx`'s existing shadow style) in `components/common/` and route those catch blocks through it.
- [ ] **33. Add optimistic UI + rollback for like/rating actions** — `like-button.tsx` and `component-ratings.tsx` currently wait on the API response before updating the displayed count/state, which reads as laggy on a slow connection. Flip to optimistic update (toggle immediately, revert + surface an error via item 32's toast if the request fails).
- [ ] **34. Standardize empty/error state layout across all pages** — Browse, `/me`, `/me/analytics`, `users/[id]`, and component detail tabs (comments, ratings, builds) each hand-roll their own empty/error block with slightly different padding, icon size, and copy tone. Extract a shared `components/common/empty-state.tsx` (icon + heading + optional CTA, brutalist border) and sweep all of them onto it, matching the pattern already established for `component-card-skeleton.tsx` in item 23.
- [ ] **35. Add visible focus states for keyboard navigation** — interactive elements throughout (nav links, buttons, badges-as-links, pagination) rely on browser-default focus rings or none at all, which is inconsistent with the site's otherwise very deliberate 2px-border visual language. Add an explicit `focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2` (black/white per theme) as a global rule in `globals.css` so keyboard users get the same crisp, high-contrast affordance mouse users get from hover states.
- [ ] **36. Add a persistent "copied" confirmation for copy-to-clipboard actions** — `install-command.tsx` and `webhook-setup.tsx` both expose copy buttons for commands/secrets; verify each gives clear, consistent visual confirmation (icon swap + label change, not just a title tooltip) and standardize the duration/style between the two so copying a git-clone command and copying a webhook secret feel like the same interaction.
- [ ] **37. Tighten mobile responsiveness on data-dense pages** — `component-card.tsx`'s footer row (license, dates, repo link, rating, owner actions) and the `/me/analytics` stat tiles wrap unpredictably on narrow viewports; audit both at 375px width and adjust `flex-wrap`/stacking so information hierarchy stays legible instead of degrading into a ragged wrap of mono-font fragments.
- [ ] **38. Add a scroll-to-top / "back to browse" affordance on long pages** — the component detail page (tabs + comments + ratings + version list can run long) and the Browse grid at high page counts have no quick way back to the top; add a small fixed-position brutalist button (bordered square, hard shadow on hover, consistent with item 25's unified hover rule) that appears after scrolling past the fold.

## Phase 7 — GitHub data enrichment

Current GitHub usage (`internal/github/handlers.go`, `internal/worker/github_source.go`) only covers auth, listing the user's repos, browsing contents/branches, and zip-downloading for builds. All items below hit public repo read endpoints already covered by the existing OAuth scope — no new GitHub permissions needed — and should go through the existing Redis cache pattern (`internal/cache`) since repo metadata is read-heavy/write-rare, same rationale as item 7.

- [ ] **39. Fetch and display real repo stats on linked components** — `GET /repos/{owner}/{repo}` gives stars/forks/open-issue counts for free; add a backend endpoint that fetches and caches this (keyed by `owner/repo`, short TTL), and surface stars/forks on `component-card.tsx` next to the existing LINKED badge and on the detail page, instead of the current binary linked/unlinked-only status.
- [ ] **40. Auto-fill license/description from GitHub instead of manual entry** — `GET /repos/{owner}/{repo}` also returns `license.spdx_id` and `description`; when linking a repo (`component-link-handler.go` flow), pre-fill the component's `license`/`description` fields from GitHub if the user left them blank, so linked components aren't stuck with placeholder text.
- [ ] **41. Add a language breakdown bar to the component detail page** — `GET /repos/{owner}/{repo}/languages` returns bytes-per-language; render as a thin horizontal segmented bar (grayscale shades only, consistent with the black/white palette) showing the repo's actual language composition, next to or replacing the manually-tagged `frameworks` list on `repository-info.tsx`.
- [ ] **42. Show the real latest commit instead of a raw SHA** — `GET /repos/{owner}/{repo}/commits?per_page=1` gives the commit message, author, and date; replace the bare 7-char SHA currently shown in `component-card.tsx`'s footer and `repository-info.tsx` with the actual commit message + relative time (e.g. "fix: typo · 3 days ago"), keeping the SHA as a secondary/hover detail.
- [ ] **43. Add a contributor avatar stack to the detail page** — `GET /repos/{owner}/{repo}/contributors` returns avatar URLs; render a small overlapping row of bordered avatar squares (matching the `Avatar.Root` pattern already used in `navbar.tsx`) on the component detail page as social proof, linking out to the GitHub contributors page.
- [ ] **44. Render the linked repo's actual README as the component's detail content** — `GET /repos/{owner}/{repo}/readme` (base64-encoded) plus the existing `components/common/markdown.tsx` (already used for changelogs in `version-list.tsx`) can render the repo's real README in a new detail-page tab, instead of relying solely on the short manually-typed `description` field.
- [ ] **45. Use GitHub's auto-generated OG image as a card banner** — `https://opengraph.githubassets.com/1/{owner}/{repo}` needs no auth/API call and returns a rendered social-preview image per repo; add it as an optional thumbnail/banner on `component-card.tsx` for linked components (with graceful fallback to the current text-only layout if the image 404s), giving Browse a visual anchor beyond mono-font text blocks.
- [ ] **46. Suggest tags from the repo's GitHub topics** — the `topics` field on `GET /repos/{owner}/{repo}` reflects topics the maintainer already set on GitHub; when linking a repo, offer these as one-click-add suggestions alongside the existing manual `tags` input, so tagging isn't purely manual duplicate effort.
